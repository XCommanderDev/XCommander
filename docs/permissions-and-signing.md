# Permissions, signing and the dev loop

This is the part of Mac development that iOS doesn't prepare you for. On iOS, permissions are
prompts with a usage string. On the Mac, XCommander needs a permission the user grants by hand
in System Settings, and that permission is tied to **how the app is signed**. If you get signing
wrong, you'll grant the permission after every build and wonder why it keeps disappearing.

## Accessibility permission (TCC)

macOS keeps privacy permissions in a database called **TCC** (Transparency, Consent and
Control). XCommander needs one entry: **Accessibility**, under System Settings → Privacy &
Security → Accessibility. Both the event tap and every Accessibility call need it.

How the app handles it (`requestAccessibilityThenStart()` in `AppDelegate.swift`):

1. On launch, it checks `AXIsProcessTrusted()`.
2. If not trusted, it calls `AXIsProcessTrustedWithOptions` with the prompt option, which makes
   macOS show its "would like to control this computer" alert once.
3. Then it **polls** every second. There's no notification when the user flips the switch, so
   polling is the only way to start working the moment they do, without a relaunch.

The first-run window (`FirstRunWindow.swift`) explains what's about to happen before macOS asks,
because the system alert is scary on its own.

Things that tripped me up:

- **The prompt only appears once per app identity.** If you dismiss it, macOS won't ask again.
  The user has to go to System Settings. The menu bar menu has an item that opens the right pane.
- **There's no API to grant it.** You can only trigger the prompt and wait.
- **The grant belongs to a code signature, not a file path.** More on that below.

A second, separate permission can appear: **Files and Folders**. If your project lives under
`~/Documents`, `~/Desktop` or `~/Downloads`, macOS asks the first time XCommander reads a file
there (for the file picker, search or the preview). That's expected. The preview pane only
reads files inside the project root the file index already listed (`PreviewLoader.swift`), so
the prompt can't fire in the middle of moving through results with the arrow keys.

## Why signing matters

TCC remembers a grant for an app's **designated requirement**, which is derived from its code
signature: roughly "this bundle ID, signed by this team's certificate". As long as every build is
signed the same way, the grant survives rebuilds.

- **Signed with your Apple Development certificate:** the identity is stable. Grant once, and
  every rebuild keeps working.
- **Ad-hoc signed** (`codesign --sign -`, what you get without a certificate): the identity is
  the hash of the binary, so it changes on every build. macOS treats each build as a new app.
  The switch in System Settings may still look *on* while the new build is refused.

If permission seems granted but nothing works: remove XCommander from the Accessibility list
(the minus button), launch it again and grant it fresh. Or reset it from Terminal:

```sh
tccutil reset Accessibility dev.xcommander.XCommander
```

## Setting up signing

The official build is signed with my team. To build under your own Apple account (a free one
works), don't edit `Config/Signing.xcconfig`. Create `Config/Signing.local.xcconfig` next to it
(git ignores it):

```
DEVELOPMENT_TEAM = YOUR_TEAM_ID
BUNDLE_ID_PREFIX = com.yourname
```

Your Team ID is in Xcode → Settings → Accounts. `Signing.xcconfig` includes the local file if it
exists, so your values win. The Xcode project reads both through `project.yml`.

## The two build paths

Both produce a signed `XCommander.app`.

### From Xcode

Open `XCommander.xcodeproj` and run the **XCommander** scheme. Good for debugging with
breakpoints.

The project is generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen) from
`project.yml`, and the generated project is committed so you don't need XcodeGen just to build.
**If you add, remove or rename files, or change a build setting, edit `project.yml` and run
`xcodegen`.** Hand edits to the project are overwritten the next time someone regenerates it.

### From Terminal

```sh
tools/xc.sh run     # build with SwiftPM, assemble the .app, sign it, launch it
tools/xc.sh stop    # quit it
tools/xc.sh logs    # stream its logs
swift test          # run the tests
```

SwiftPM can build the executable but can't make an app bundle, so `xc.sh` assembles one by hand:
it writes the `Info.plist`, copies the binary, compiles the asset catalogue and the app icon with
`actool`, and signs the bundle with your first "Apple Development" certificate (or ad-hoc if you
have none). The bundle is built in `~/Library/Caches/XCommander/`, outside `~/Documents`, because
building there adds extended attributes that make `codesign` fail.

This path is faster for small changes and is what I use day to day.

**Use one path at a time.** Both builds have the same bundle ID. Running both copies at once
means two event taps fighting over the same keys.

## Hardened runtime, notarization and releasing

None of this is needed to build and use XCommander yourself. It's the checklist for publishing
a build other people can download.

- **Hardened runtime** is already on (`ENABLE_HARDENED_RUNTIME: YES` in `project.yml`). Apple
  requires it for notarization. XCommander loads `sourcekitd` and the index store library out
  of Xcode at runtime with `dlopen`, so check whether the release build needs the
  *Disable Library Validation* entitlement for those to load.
- **Developer ID.** Apps distributed outside the App Store are signed with a *Developer ID
  Application* certificate (from a paid Apple Developer account), not the development one.
- **Notarization.** Upload the signed app (zipped or in a DMG) with
  `xcrun notarytool submit … --wait`. Apple scans it and returns a ticket.
- **Stapling.** `xcrun stapler staple XCommander.app` (or the DMG) attaches the ticket, so the
  app opens without a network check.
- **No sandbox, no App Store.** An event tap can't exist in the App Sandbox, so XCommander is
  distributed directly.
- **Updates.** [Sparkle](https://sparkle-project.org) is the standard for apps outside the App
  Store.

`Design/XCommander.icns` (generated by `tools/icons.sh`) is there for the DMG's volume icon.
